- (capability) CAP-2 one command, uv run python load_seed.py, loads seed/tickets.csv and seed/customers.csv into app.db as tables tickets and customers with the CSV columns; running twice gives the same database; success: after one run app.db has 24 tickets and 20 customers rows with the CSV headers as columns, a second run leaves identical contents, and get_ticket('T-1042') from mcp/triage_server.py returns customer C-77

- (constraint) seed/ is read-only; the loader only reads it
- (constraint) no network calls and no API keys anywhere in Epic 1
- (constraint) mcp/triage_server.py already reads app.db at the repo root, querying tickets(ticket_id, customer_id, created_at, text) and customers(customer_id, name, plan, open_tickets); those table names, column names and the file location must keep working, and the server file is not changed

- (constraint) the schema is the decision contract Epic 2's agent returns as structured output and Epic 3's eval checks, so it must be importable from Python by both
- (non-goal) the agent, the MCP tools, evals and any user interface are out of scope
- (assumption) the schema is a Pydantic model (pydantic is already a project dependency), so Epic 2 can pass it straight to the agent as structured output
- (assumption) unknown extra fields are rejected, reading 'anything else is rejected' literally
- (assumption) open_tickets is stored as an integer, since the Enterprise rule compares it against 3; every other column is stored as text

- (question) how strictly is 'one-sentence rationale' enforced: non-empty string only, or also rejecting multi-sentence text?
